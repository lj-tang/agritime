> 3. 新增 **T17 用户数据持久化**：终结 localStorage + JSON 文件的临时方案，地块/作物/工单/账号统一入库并支持跨设备。
> 4. 新增 **T18 可观测性与性能守门**：p95、上游健康、降级次数、缓存命中率要有面板，性能不再靠人工 curl。
> 5. 补齐 V4 未达标项：T02 / T03 / T04 / T07 / T08 / T09 / T11 / T13。
> 6. **目录规范按实际落地修订**：不拆 SPA 子目录，`shared/utils` 已落地并接入线上（详见第二章差异说明）。

## 一、项目整体目标（V5）

围绕三条主线收口：

1. **数据可信**：每一条展示给用户的数据，都能回答"从哪来、多久更新一次、取不到时怎么办"。拿不到的数据就明确显示"无数据"，不用默认值凑分，不用随机数伪装。
2. **验收收口**：V4 复盘里 8 项未完全达标的功能全部补齐，让 16 个模块的每一条验收标准都能当场复现。
3. **多端与运维**：小程序端可用、用户数据可跨设备、性能与上游健康可观测。

技术基线保持不变：零第三方依赖（JDK 自带 + 原生前端）、核心接口 p95 < 2s、所有外部依赖必须有三档降级。

### 与 V4 规范的差异及原因

#### 模块4：时间体系补齐
**任务编号：T04**

- **任务描述**：
  1. **日期范围**：未来 10 天 → **30 天**；过去 2 年保持不变。范围统一收口到 `shared/utils/date-window.js`，`index.html` 与 `timeline.html` 都调它，禁止各写一份
  2. **播种起点双模式**：
     - 方式 A（默认）：用户不填日期 → 按「地点 + 作物」取最近一个适宜播种的节气，返回 `sowDateSource: "solar-term"` 并说明依据（哪个节气、距今天数）
     - 方式 B：用户填日期 → 从该日期向后生成，`sowDateSource: "manual"`
  3. **过去日期走历史数据**：`Open-Meteo Archive API` 已实测可用。过去 2 年的节点用历史实测天气，不用预报数据；请求失败时降级为气候均值并标注
  4. **第 5 天起标注**：未来第 5 天（含）之后的节点/天气展示，统一标注"天气为预测数据，仅供参考"。`DateWindow.needsForecastNote()` 已就绪，需真正渲染到页面上
  5. **关键节点提醒**：浇水/施肥/病虫害防治/采收节点可开启提醒，前端展示倒计时；到点用 `Notification API`（无权限时退化为站内横幅）
- **验收标准**：
  1. 日期选择器上限为今天 +30 天，第 31 天不可选
  2. 不填日期时能生成完整日历，并显示"按节气芒种起算（距今 X 天）"
  3. 过去日期的节点标注"历史实测"，未来 1–4 天标注"预报"，第 5 天起标注"预报·仅供参考"
  4. 开启提醒后刷新页面仍保留，倒计时正确递减
  5. 天气接口不可用时仍能生成完整日历，无"天气数据暂不可用"弹窗
- **对应目录**：`shared/utils/date-window.js` / `backend/service/weather` / `frontend/components/reminder` / `frontend/pages/timeline.html`

## 七、开发与认领规则

1. **全栈认领**：每人认领完整模块，从数据、后端接口到前端页面全链路负责
2. **提交规范**：一个模块一次提交，commit message 写清「做了什么 / 为什么 / 怎么验证」；不提交 `.dev/`、密钥、截图
3. **数据红线**：新增任何展示数据，必须同时在 `data/sources/registry.json` 登记来源，否则不予合入
4. **测试要求**：每个模块至少补 3 条断言到 `frontend/tests/pages.test.js`；后端改动必须能通过 `deploy.sh` 的编译
5. **部署纪律**：**不允许直接在服务器上改文件**。`deploy.sh` 会 `reset --hard` 覆盖手工改动；所有变更走 git
6. **联调节点**：每批完成后做一次全链路联调，按第八章验收
