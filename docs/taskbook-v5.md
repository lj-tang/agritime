**版本**：V5.1（替代 V5.0）
**日期**：2026-10-30
**基线**：`95916ee`，线上 `b70abab`，`frontend/tests/pages.test.js` 136 项断言全绿
**适用范围**：全员。仓库收敛至 `agritime/`，按功能模块认领，不严格区分前后端

> **为什么有 V5.1**
>
> V5.0 把重心放在了横向工程能力上（T16 数据治理 / T17 持久化 / T18 可观测 / T19 气象提醒）。

> 拍照只回一个作物名、日历确认播种后我的作物里什么都没有。
>
> V5.1 把顺序倒过来：**先让 V4 的每个功能真正落地、闭环、可解释，再谈新增。**
> T19 保留，但降为 P2，且必须先有 P0 的作物与提醒底座。

## 一、先回答：功能强化到底在哪

### 1.1 V5.0 的"强化"为什么感知不到

| V5.0 内容 | 性质 | 用户感知 |
| --- | --- | --- |
| T16 数据来源登记 | 工程治理 | 只在角标上体现，且多数页面没接 |
| T17 地块/作物上云 | 基础设施 | 跨设备时才有感，单机用户无感 |
| T18 p95 / 缓存 / 健康检查 | 运维能力 | 完全不感知，只保证"不崩" |
| T19 气象提醒 | 功能 | 有感，但依赖作物档案与地块数据，而这两块本身没闭环 |

**结论**：上一版把"不出事故"当成了"功能强化"。真正的强化应该发生在
**用户每天要点的那几个按钮背后**——输入的默认值、结果的理由、建议的剂量、失败时的说明。

### 1.2 成熟度口径

本文用四级衡量功能，不再用"完成/未完成"二元判断：

| 等级 | 定义 | 典型表现 |
| --- | --- | --- |
| **L0 空壳** | 有入口无有效数据 | 点开是空白或固定占位 |
| **L1 可用** | 主流程能走通，但信息单薄、要用户手填、无上下游联动 | "能出结果，但我不信" |
| **L2 好用** | 默认值合理、结论有依据、失败有兜底 | "不用教就会用" |
| **L3 闭环** | 与上下游互相驱动：地块→推荐→日历→作物→提醒→复盘 | "离不开" |

## 二、V5.1 主线：五条用户可感知的价值线

1. **输入成本归零**：地点说人话就够，坐标、播期、面积都有合理默认值。
2. **结论可核对**：每个数字能点开看来源，每条建议能说出"因为"。
3. **链路闭环**：推荐→日历→我的作物→提醒→复盘，数据只录一次。
4. **建议可执行**：给到"做什么 + 怎么做 + 用多少 + 什么时候停"。
5. **不懂就说不懂**：缺数据时明确说缺什么、怎么补，绝不拿默认值冒充结论。

后文所有改造项，都必须落到这五条之一；落不到的，不进 P0。

## 三、P0：V4 功能落地（本轮主战场）

### P0-1 T15 种植推荐：从"静态打分表"到"能解释的决策"（L1→L3）

**现状问题**

- `frontend/assets/js/recommend.js:52` 提交时只读 `latInput/lonInput`，用户输入的"山东济宁"被完全忽略；
  经纬度默认 `35.07/116.31`（`index.html:141-147`），于是全国用户看到同一份结果。
- `data/market/recommend-rules.json` 仅 25 条，`market: 88` 是手写整数，没有时间、区域、品种维度。
- `RecommendHandler.score()`：月份 60 + 纬度 25 + 市场 15，**无地块、无茬口、无投入产出**。
- 结果页只展示一个总分和一句 `reason`，用户无法判断"凭什么它第一"。

**改造项**

1. **地点即刻解析**：提交时若地点文本变化且坐标未被手动修改，先调
   `GET /api/geo/search?q=<地点>` 取首条 `lat/lon`；失败才提示"请手动填坐标"。
   经纬度输入折叠进"高级选项"，默认不展示。
2. **评分重构**（`RecommendHandler.score()`）：

   | 因子 | 权重 | 说明 |
   | --- | --- | --- |
   | 播期匹配 | 45 | 命中月份满分，前后 1 个月线性衰减 |
   | 气候带匹配 | 20 | 纬度落在 `latRange` 内 |
   | 热量条件 | 10 | 由纬度和月份估算积温区间，落在作物需求内得分 |
   | 市场热度 | 15 | 改为 `high/medium/low` 三档，不再用 88 这种假精确 |
   | 地块适配 | 10 | 传入 `plotId` 时复用地块适宜度；无地块则权重归一 |

3. **市场数据降级为等级**：`market` 字段改为 `marketLevel` + `marketBasis`
   （例："叶菜类四季度批发价同比 +6%，属常规需求"）。数据来源登记为"经验规则"，
   界面不写成"实时行情"。真实行情需另接批发市场价格源，本轮不做，但**必须标明**。
4. **理由结构化**：响应 `reasons: [{type:"solar"|"climate"|"market"|"plot", text:"…", basis:"…"}]`，
   前端按类型分组，不再是一段散文。
5. **给出对比**：返回 `runnerUp`（第二名作物）与 `gapReason`（"番茄比辣椒高 8 分，主要差在播期窗口更宽"）。
6. **一键落历**：`/api/recommend` 返回 `suggestedSowDate`，前端跳转时预填作物与播期，
   而不是只 `switchModule('calendar')`（当前 `recommend.js:185` 只切面板）。

**验收**

1. 输入"山东济宁"不填经纬度，结果与输入"广州"不同，且页面显示"已定位到 35.41, 116.59"。
2. 每条推荐至少 2 条理由，可展开看到 `basis`。
3. 第一名卡片显示与第二名的分差原因。
4. 点"用它排日历"，日历表单作物、日期、地点三项已填好。
5. `market` 不再出现 0–100 的精确数字；`docs/api.md` 同步更新字段。

### P0-2 T12 我的作物：把"能连上"做成"连得稳"（L1.5→L2）

> **进度（2026-10-30）**：缺口 1/2/4 与来源徽标、地块名已修，`pages.test.js` 137 项全绿；
> 生长曲线、下一次作业仍待做。

**现状问题**（已核对，链路存在，缺口在细节）

链路是通的：`timeline.html:269` 点「确认已播种」→ `postMessage` → `sowing-bridge.js` 同源校验
→ `my-crops.js:19` 写入 `MyCropsStore`。但有 4 个缺口，导致"能用但不好用"：

- **无去重**：监听器直接 `add`。用户重新进日历再点一次，就多一条一模一样的记录。
- **信息缺失**：`detail` 只带 `cropName/cropId/sownDate`，不带 `location/plotId`，
  记录与地块的关联永远为空，V4 验收第 4 条"按作物/地块关联展示"实际做不到。
- **拍照不留痕**：`handlePhoto()` 只 `patch {cropName}`，`photoHistory` 字段虽在 store 里初始化，
  但**从未被写入**，无法回看长势变化。
- **地块显示裸 ID**：卡片 `地块：' + r.plotId`，用户看到的是 `p_xxx`。

**改造项**

1. **去重建档**：`my-crops.js` 监听器里按 `cropName + sownDate` 查重，已存在则更新
   `updatedAt` 并提示"该作物已在记录中"，不再新增。
2. **补全上下文**：`timeline.html` 的 `detail` 增加 `location`（`query.location`）与
   `plotId`（从 URL 或地块选择器取）；`my-crops.js` 一并写入。
3. **来源徽标**：记录增加 `source: 'calendar' | 'manual' | 'photo'`，卡片显示
   "来自日历 / 手动添加"，用户知道数据从哪来。
4. **拍照落痕**：`handlePhoto()` 写入 `photoHistory: [{at, crop, confidence}]`，
   同时仅在 `cropName` 为空时补全，**不覆盖**用户手填的高度与长势。
5. **生长曲线**：同一记录的高度记录 ≥2 个点时画折线（纯 SVG，不引库）；
   不足 2 点显示"再记录一次即可看趋势"。
6. **地块名可见**：卡片通过 `MyPlotsStore` 查 `plotId` 对应名称，查不到显示"未关联地块"。

**验收**

1. 日历「确认已播种」后返回首页，"我的作物"立即出现该记录，来源标"来自日历"。
2. 同一作物同一天重复确认，记录数不增加，只更新 `updatedAt`。
3. 连续两次拍照后 `photoHistory` 有两条记录（含时间与置信度），且不覆盖手填的品种与高度。
4. 记录关联地块后，卡片显示地块名，查不到时显示"已关联（地块已删除）"。
5. 详情页"下一次作业"与时间线节点一致（待做）。

### P0-3 T13 病害检测：从"关键词命中"到"问诊"（L1.5→L2）

**现状问题**

- 输入靠一段自由文本，`DiseaseHandler.score()` 做关键词计数；用户不知道该怎么描述。
- `confidence` 直接输出 0.42 这类小数，看似精确，实则是关键词命中比例。
- `data/disease/library.json` 仅 14 条，字段无"危害部位""安全间隔期""每季最多施用次数"。
- 防治方案是 `treatment[]` 三段话，没有剂量、没有采收前禁用期。

**改造项**

1. **结构化问诊**：作物（必填，走 `CropRegistry` 归一）+ 危害部位（叶/茎/果/根/整株）+
   症状多选（褐斑/黄化/白粉/萎蔫/虫孔/腐烂/畸形）+ 环境（连续阴雨/高温干旱/低温高湿/不明）。
   自由文本保留为"补充描述"。
2. **置信度分档**：输出 `confidenceLevel: high|medium|low` + `confidenceBasis`
   （"命中 4 条症状中的 3 条，且作物吻合"），界面不展示小数。
3. **依据可查**：`matchedSymptoms[]` 与 `missingSymptoms[]` 同时返回，用户知道"为什么不是另一个"。
4. **方案分层**：`control: {cultural[], biological[], chemical[]}`；
   `chemical[]` 每条含 `agent`（药名）、`formulation`（剂型）、`dilution`（稀释倍数）、
   `safetyIntervalDays`（安全间隔期）、`maxApplicationsPerSeason`。
5. **安全提示**：采收前 `safetyIntervalDays` 天内禁用；高温 >32℃ 或大风 >4 级提示"暂缓施药"。
6. **数据补口**：`library.json` 从 14 条扩到 ≥30 条（覆盖 5 个主栽作物），
   老条目补 `parts`、`safetyIntervalDays`；缺字段的条目在界面标"方案为通用建议"。
7. **图片定位不变**：仍为颜色特征辅助排序，界面维持"仅辅助排序，未做病斑识别"的说明。

**验收**

1. 选"番茄 + 叶片 + 褐斑 + 连续阴雨"，Top1 为晚疫病，依据列出命中的 3 条症状。
2. 每条化学防治都有安全间隔期与每季最多次数。
3. 采收期（距采收 < 安全间隔期）提交时，方案顶部出现禁用提示。
4. 无匹配时返回"建议补充：部位/颜色/是否有霉层"，不是空列表。
5. 库内 ≥30 条，缺字段条目有"通用建议"标记。

### P0-4 T14 客服：补状态机、分页与后台入口（L1.5→L2）

**现状问题**

- `SupportHandler.tickets()` 一次返回全部工单（125–142 行），无 `page/size/total`。
- 状态只有 `open/closed`，用户回复后状态不变，超管无法区分"待处理/已回复"。
- 用户端无未读提示，回复了也不知道。
- `admin.html:46` 明确写着"客服工单管理在主页的客服面板里"，后台没有独立工单页。

**改造项**

1. **状态机**：`open → replied → resolved → closed`；用户可"标记已解决"，超管可关闭/重开。
   用户新增回复时 `replied → open`（重新待处理）。
2. **分页**：`GET /api/support/tickets?page=1&size=20&status=open`，
   返回 `{items, page, size, total, hasMore}`；前端"加载更多"。
3. **未读**：工单存 `lastReadAtByUser` / `lastReadAtByAdmin`；列表项显示红点与未读数，
   打开详情即更新。侧栏客服入口显示总未读。
4. **后台独立页**：`admin.html` 增加"工单"tab（列表 + 状态筛选 + 详情 + 回复 + 关闭），
   不再跳回主页。
5. **自助前置**：提交前展示 3 条高频问题（账号登录、数据不显示、提醒收不到），
   点击展开答案；未解决再提交，减少无效工单。

**验收**

1. 21 条工单时第一页 20 条、`hasMore=true`，翻页取到第 21 条。
2. 超管回复后用户端铃铛/入口红点 +1，打开详情归零。
3. 用户"标记已解决"后状态为 `resolved`，超管列表可按状态筛出。
4. 后台可完成"查看→回复→关闭"全流程，全程不离开 `admin.html`。

### P0-5 T03 农事指导：让建议带上"因为"和"用多少"（L1.5→L2）

**现状问题**

- `GuidanceService` 浇水仅三档（rainy/default/drought），依据是一句"累计降雨约 X mm"；
- 施肥剂量来自 `data/guidance/guidance.json` 固定值，与地块面积无关——2 亩和 20 亩给同样用量；
- 农具清单只有名字，没有"为什么这个节点需要它"。

**改造项**

1. **按面积换算**：地块有 `area` 时，输出"你这块 2.3 亩，需 40% 代森锰锌 92 g，兑水 45 kg"；
   无面积时给"每亩用量"，并提示"填写地块面积可自动换算"。
2. **依据行**：每条浇水/施肥建议附 `basis`（"窗口累计降雨 12 mm，土壤含水率 0.11，低于持水下限"）。
3. **剂量安全边界**：施肥给出上限（"不超过 8 kg/亩，过量易烧根"）；施药给安全间隔期。
4. **农具解释**：`tools: [{name, why}]`，例如"喷雾器：叶面均匀着药，早晚无风时作业"。
5. **天气冲突拦截**：窗口内有雨且建议施药时，自动追加"雨前 6 小时内不要喷药，药液会被冲刷"。

**验收**

1. 同一作物、同一节点，地块 2 亩与 10 亩的用量数字不同。
2. 每条浇水/施肥建议都有 1 行 `basis`，数值与时间线天气一致。
3. 有雨窗口的施药建议包含"雨前禁喷"提示。
4. 农具清单每项有用途说明。

### P0-6 T06 我的地块：让建模参数真的影响结论（L2→L2+）

**现状问题**

- `farmingSuitability()` 五因子（气候 0.30 / 土壤 0.30 / 水质 0.20 / 地形 0.10 / 类型 0.10），
  `shape`（方形/条状/不规则）**未进计算**，只有 `angle/slope/terrace` 参与；
- 只给一个总分和分项分，不告诉用户"最该改哪一项"；
- 没有"这块地适合种什么"，与推荐模块割裂。

**改造项**

1. **形状进计算**：新增"机械化便利度"因子（权重 5%，从地形里分出）：
   方形 100 / 条状 85 / 不规则 70；梯田 +5（小块可用小型机械）。
2. **限制因子**：取最低分项，输出 `limiting: {key, score, advice}`，
   例如"土壤 58 分：偏砂，保水差，建议增施有机肥或改滴灌"。
3. **作物适配 Top5**：`GET /api/plots/adapt?lat=&lon=&type=&soil=` 复用推荐引擎，
   按地块条件排序，给"最适合/可以种/不建议"三档。
4. **与推荐联动**：地块详情"适合种什么"点击后带 `plotId` 跳推荐页，推荐结果按该地块重算。

**验收**

1. 同一地块把形状从"方形"改为"不规则"，总分变化且机械化因子分数不同。
2. 详情页显示限制因子与一条改良建议。
3. 地块详情能看到 Top5 适宜作物，点击可带地块进推荐。

## 十一、V5.2 真实分析深化（已落地）

这一节的起因是一句批评：**"地块要能在地图上真框选，我们也能真分析用户框的地；
我的作物要能真知道种成什么样；渔业要真知道水质和鱼的状态，别做鸡肋。"**
下面三项都已通过真实数据源落地，不是 UI 装饰。

### 11.1 T06+ 地块：3D 框选 + 多边形空间分析

**新增**：`frontend/components/plot-3d/`（MapLibre GL，卫星底图 + AWS Terrarium DEM 地形起伏）、
`backend/.../api/PlotAnalyzeHandler.java`（`POST /api/plots/analyze`）。

| 环节 | 以前 | 现在 |
| --- | --- | --- |
| 框选 | Leaflet 2D，只做土地性质校验 | 3D 地形上按真实边界描点，实时面积/周长 |
| 面积 | 手填 | 球面投影 shoelace 实算（亩/m²/周长/紧凑度） |
| 坡度 | 手填倾角/坡度，且不进评分 | DEM 网格采样（≤30 点）+ 最小二乘平面拟合，出坡度与坡向 |
| 土壤 | 质心单点 | 质心取 0cm/6cm 地温与 0-1cm 体积含水率（Open-Meteo 土壤模型，非区域假设值） |
| 评分 | 五因子加权，手填参数 | 地形/土壤/气候/形状规模/排水保水五因子，缺数据项不参与并重新归一 |
| 输出 | 一个分数 | 分项分解 + 限制因子（高/中/低）+ 可执行改良建议 + 适宜作物 Top5 |

适宜作物不是写死清单，而是拿 `properties.json` 的 `suitableRegion / suitableSeason / tempRequirement`
与这个地块的区划、坡度、墒情、当前月份逐一匹配打分。

### 11.2 T12+ 我的作物：真实生长状态

**新增**：`backend/.../api/CropStatusHandler.java`（`GET /api/crop-status`）。

- 阶段不靠"过了多少天 ÷ 全生育期"拍脑袋，而是 **今年活动积温 ÷ 去年同期积温** 做校正，
  能说出"比常年提前/推迟 N 天"（数据不足时降级为日历进度并明示）。
- 播种日至今的气温与降水来自 Open-Meteo 归档实测，不是预报填充。
- 当前/下一个农事节点取自真实规程 `crop-protocols.json`。
- 本周 3 条做法结合未来 7 天预报生成（雨前追肥、停灌排渍、高温/霜冻应对）。

### 11.3 T09+ 渔业：鱼塘水质与投喂

**新增**：`backend/.../api/PondStatusHandler.java`（`GET|POST /api/pond-status`）。

- 水温：气温 3 天滑动均值 × 0.85 + 1.0，标"模型估算"。
- 溶氧：饱和溶氧二次式 × 天气折减系数（阴雨/闷热/大风/高温），
  **单独报凌晨最低值** —— 泛塘发生在凌晨，只报日均会害人。
- 投喂：存塘量（面积 × 密度 × 规格）× 水温决定的日投喂率，算出今天喂多少公斤；
  凌晨溶氧跌破 2 mg/L 时直接停料，与"开增氧机"动作不再自相矛盾。
- 用户填的 pH/氨氮/溶氧**优先于估算值**，返回里标 `实测` / `模型估算`，不让估算冒充实测。

### 11.4 诚实性约定（三条都不能破）

1. 取不到的数据不参与评分，权重重新归一，不用默认值假装测到。
2. 模型推算的值必须标"估算"，并说明推算依据（如"饱和溶氧 × 70%，连日阴雨光照不足"）。
3. 前端不再出现"未取到就编一个"的兜底分数。
