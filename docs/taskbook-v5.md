# 会看天的农事日历 · 功能强化与补齐任务书 V5

**版本**：V5.0
**日期**：2026-10-31
**适用范围**：全员功能开发，统一收敛至 `agritime/` 目录，不分前后端，按功能模块认领
**编号规则**：V4 已占用 T00–T15，本任务书自 **T16** 续接，共 14 项，全部为待开发任务

> **V5 变更说明（相对 V4）**：
>
> V4 解决的是"功能有没有"，V5 解决的是"功能准不准、连不连得上"。四版下来仍有四类硬伤：
>
> 1. **判断不设防**：日历对输入照单全收，推荐不看地点，病害给个 0.42 的伪精确分数 —— 系统在替用户做它没能力做的判断。
> 2. **数据是断的**：指导剂量不随面积变，茬口不校验，地块没有历史，传感器只存本机 —— 每个页面都只知道自己那一小块。
> 3. **闭环缺最后一环**：提醒只存在 localStorage，工单没有状态流转，日历节点只能看不能改 —— 用户看完还得自己记。
> 4. **工程欠账**：23 处时间调用只有 2 处显式时区，天气失败仍返回一份看起来正常的日历，所有档案都存在浏览器里。
>
> 本版 14 项任务全部指向这四类问题，不含新建大模块。

## 一、项目整体目标

围绕**判断可信、数据连通、闭环可用**三条主线补齐：

- **判断可信**：每个结论都能追溯到数据来源与计算口径；说不准的地方明确说"说不准"，不用默认值蒙混。
- **数据连通**：同一份数据在推荐、日历、指导、地块之间流动，用户填一次就够；跨会话、跨设备不丢。
- **闭环可用**：提醒能落地、工单能流转、节点能调整、收获能核算 —— 用户在这个系统里能把一季农活走完。

性能与降级要求沿用 V4：核心接口 p95 < 2s，外部依赖具备三档降级。

### 模块16：病害问诊深化
**任务编号：T16**
**优先级**：P1
- **任务描述**：
  1. 病害库由当前 14 条扩充至覆盖 5 个主栽作物、不少于 50 条，每条标注来源与适用范围
  2. 置信度改为"匹配度"，并列出命中的症状关键词，不再显示无解释的小数
  3. 每条防治方案补充安全间隔期、施药安全与抗性管理提示
  4. 图像识别维持颜色特征辅助，界面明确"仅辅助判断"，不承诺识别率
  5. 无匹配结果时提供"转人工/客服"入口，不硬凑 Top3
- **验收标准**：
  1. 查询"小麦条锈病"返回 Top1，症状描述与该病一致
  2. 结果展示命中依据（如"叶片黄色条状孢子堆"），不出现无解释的分数
  3. 每条用药建议带安全间隔期（天）
  4. 输入无关描述时返回"未匹配到"，并给出转人工入口
- **对应目录**：`data/disease/library.json` / `backend/api/DiseaseHandler` / `frontend/assets/js/disease.js`

### 模块17：农事指导按面积与墒情换算
**任务编号：T17**
**优先级**：P0
- **任务描述**：
  1. 指导剂量按地块面积换算，同时输出亩均用量与总面积用量
  2. 结合当前墒情与未来降水调整：雨前施用、干旱补灌、过湿排渍

- **验收标准**：
  1. 同一作物 2 亩与 20 亩给出不同的总用量，亩均量一致
  2. 未来 3 天有雨时出现"雨前施用"建议，连续无雨时出现"补灌"建议
  3. 指导内容随节点类型变化（施肥/灌溉/打药/收获各不相同）
  4. 无面积数据时不报错，文案提示补录面积

### 模块22：茬口冲突校验
**任务编号：T22**
**优先级**：P0
- **任务描述**：
  1. 生成日历时读取该地块已有作物记录，检查新播期与该地块上一季的收获期是否重叠
  2. 重叠时阻断并给出可用的最早播期；同一地块多季连作时给出轮作建议
  3. 校验同一用户在不同地块上的时间冲突（同一人不能同时管理两块地的重叠重活）
  4. 校验逻辑复用播种校验的三级判定口径（阻断/提醒/通过）
- **验收标准**：
  1. 地块已有 6 月 1 日播种、10 月 1 日收获的玉米时，再排 9 月 15 日播种的小麦会被阻断
  2. 阻断提示写明冲突的是哪条记录、冲突区间、建议最早播期
  3. 同一用户两块地农忙期重叠时给出提醒，但不阻断
  4. 无关联地块时校验直接通过，不额外报错
- **对应目录**：`backend/service/plot/PlotHistory`（新建）/ `backend/api/SowCheckHandler` / `frontend/pages/index.html`

### 模块23：播期建议升级
**任务编号：T23**
**优先级**：P1
- **任务描述**：
  1. 播期建议从"只看节气"升级为双依据：节气窗口 + 当年积温达标日
  2. 积温依据用近年同期实测气温推算，达到品种所需活动积温的最早日期作为第二个建议值
  3. 结合作物熟期给出"最晚播期"，避免生育后期撞霜冻
  4. 两个建议值都给出理由，由用户选择，不替用户拍板
- **验收标准**：
  1. 建议面板同时显示"按节气：X 月 X 日"与"按积温：X 月 X 日"，各带一句依据
  2. 给出的最晚播期与该地常年初霜日、作物全生育期自洽
  3. 积温数据缺失时只显示节气建议，并注明"积温数据不足"
  4. 用户选定后可一键填入日历
- **对应目录**：`backend/api/SowWindowHandler` / `backend/service/weather/ClimateNormals` / `frontend/pages/index.html`

## 五、开发与认领规则

1. **全栈认领**：每人认领完整功能模块，从数据、后端接口到前端页面全链路负责
2. **优先级顺序**：
   - 第一批（用户主链路）：T17 指导换算、T22 茬口校验
   - 第二批（判断质量）：T16 病害问诊、T23 播期建议、T26 因子增补
   - 第三批（服务闭环）：T18 提醒、T19 工单
   - 第四批（档案与设备）：T25 地块历史、T27 传感器拉取、T28 养殖核算
   - 第五批（体验与工程）：T20 四态与移动端、T21 工程兜底、T24 节点编辑、T29 持久化
3. **提交规范**：每个模块完成后提交对应目录代码，附带自测说明与验收条目逐条对照
4. **诚实性红线**（评审必查）：
   - 取不到的数据不得用默认值参与评分
   - 模型推算值必须标注"估算"并说明依据
   - 前端不得在接口失败时编造兜底分数或结论
5. **联调节点**：第一批完成后做一次「地块 → 日历 → 指导 → 我的作物」主链路联调；第三批完成后做提醒与工单闭环联调；第五批完成后做断网与跨设备联调
6. **验收节点**：每批完成后按验收标准逐条勾选，未达标不得标记完成

## 六、最终验收标准

1. 14 个任务（T16–T29）按各自验收标准可复现验证
2. 核心接口 p95 < 2s，外部依赖（DEM、天气、土壤、归档气象、设备接口）均具备三档降级
3. 用户主链路「我的地块 → 种植推荐 → 农事日历 → 我的作物 → 病害检查 → 客服」完整可走通，且数据在各环节之间连贯
4. 任一页面在断网、数据缺失、部分数据三种异常下都不白屏、不编造结论
5. 同一业务概念只有一处实现：区划、播季、面积换算、鱼种、上游解析、气候常年值
6. 提醒、工单、节点改期三条闭环均可跨会话使用，不依赖单次页面会话
7. 数据可跨设备访问，服务不可用时可降级读本地并明确提示
8. 公网地址可正常访问，账号与超管后台可用
