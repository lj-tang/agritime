# 会看天的农事日历 · 功能强化与补齐任务书 V5

**版本**：V5.0
**日期**：2026-11-03
**适用范围**：全员功能开发，统一收敛至 `agritime/` 目录，不分前后端，按功能模块认领
**编号规则**：V4 已占用 T0–T15，本任务书自 **T16** 续接，共 8 项，全部为待开发任务

> **V5 变更说明（相对 V4）**：
>
> V4 解决的是"功能有没有"，V5 解决的是"功能准不准、连不连得上"。四版下来仍有四类硬伤：
>
> 1. **判断不设防**：日历对输入照单全收，推荐不看地点，病害给个 0.42 的伪精确分数 —— 系统在替用户做它没能力做的判断。
> 2. **数据是断的**：指导剂量不随面积变，茬口不校验，地块没有历史，传感器只存本机 —— 每个页面都只知道自己那一小块。
> 3. **闭环缺最后一环**：提醒曾只存在 localStorage（本版已修），工单曾没有状态流转（本版已修），日历节点曾只能看不能改（本版已修） —— 用户看完还得自己记。
> 4. **工程欠账**：23 处时间调用只有 2 处显式时区，天气失败仍返回一份看起来正常的日历，所有档案都存在浏览器里。
>
> 本版 8 项任务全部指向这四类问题，不含新建大模块。

## 一、项目整体目标

围绕**判断可信、数据连通、闭环可用**三条主线补齐：

- **判断可信**：每个结论都能追溯到数据来源与计算口径；说不准的地方明确说"说不准"，不用默认值蒙混。
- **数据连通**：同一份数据在推荐、日历、指导、地块之间流动，用户填一次就够；跨会话、跨设备不丢。
- **闭环可用**：提醒能落地、工单能流转、节点能调整、收获能核算 —— 用户在这个系统里能把一季农活走完。

性能与降级要求沿用 V4：核心接口 p95 < 2s，外部依赖具备三档降级。

## 三、功能任务拆解

### 模块16：病害问诊深化
**任务编号：T16**
**优先级**：P1
- **任务描述**：
  1. 病害库由当前 14 条扩充至覆盖 5 个主栽作物、不少于 50 条，每条标注来源与适用范围
  2. 置信度改为"匹配度"，并列出命中的症状关键词，不再显示无解释的小数
  3. 每条防治方案补充安全间隔期、施药安全与抗性管理提示
  4. 图像识别维持颜色特征辅助，界面明确"仅辅助判断"，不承诺识别率
  5. 无匹配结果时提供"转人工/客服"入口，不硬凑 Top3
- **验收标准**：
  1. 查询"小麦条锈病"返回 Top1，症状描述与该病一致
  2. 结果展示命中依据（如"叶片黄色条状孢子堆"），不出现无解释的分数
  3. 每条用药建议带安全间隔期（天）
  4. 输入无关描述时返回"未匹配到"，并给出转人工入口
- **对应目录**：`data/disease/library.json` / `backend/api/DiseaseHandler` / `frontend/assets/js/disease.js`

### 模块17：农事指导按面积与墒情换算
**任务编号：T17**
**优先级**：P0
- **任务描述**：
  1. 指导剂量按地块面积换算，同时输出亩均用量与总面积用量
  2. 结合当前墒情与未来降水调整：雨前施用、干旱补灌、过湿排渍
  3. 灌溉建议给出方式（滴灌/喷灌/漫灌）、时长与总水量
  4. 未填面积时按亩给量，并提示"填入面积可自动换算"
- **验收标准**：
  1. 同一作物 2 亩与 20 亩给出不同的总用量，亩均量一致
  2. 未来 3 天有雨时出现"雨前施用"建议，连续无雨时出现"补灌"建议
  3. 指导内容随节点类型变化（施肥/灌溉/打药/收获各不相同）
  4. 无面积数据时不报错，文案提示补录面积
- **对应目录**：`backend/service/guidance/GuidanceService` / `backend/api/TimelineHandler` / `frontend/pages/timeline.html`

### 模块18：工程兜底
**任务编号：T18**
**优先级**：P3
- **任务描述**：
  1. **时区显式化**：全后端时间调用统一使用 `Asia/Shanghai`，不再依赖容器默认时区
  2. **去掉看起来正常的假兜底**：天气全部失败时，日历不得返回一份看似正常的计划，页头须标注"天气未获取"
  3. **推荐结果缓存**：同一地点同一天复用，避免重复计算与重复请求
  4. 外部请求超时统一从配置读取，不在各接口里各写各的
- **验收标准**：
  1. 容器以 `TZ=UTC` 启动时，"今天"仍为北京时间，节气与提醒日期不偏移
  2. 断开外网后生成日历，页头显示"天气未获取"，节点状态为"待人工判断"
  3. 同地点连续两次推荐，第二次响应 < 300ms
  4. 全仓只有一处定义默认超时值
- **对应目录**：全后端 / `backend/config/AppConfig` / `deploy/`

### 模块19：茬口冲突校验
**任务编号：T19**
**优先级**：P0
- **任务描述**：
  1. 生成日历时读取该地块已有作物记录，检查新播期与该地块上一季的收获期是否重叠
  2. 重叠时阻断并给出可用的最早播期；同一地块多季连作时给出轮作建议
  3. 校验同一用户在不同地块上的时间冲突（同一人不能同时管理两块地的重叠重活）
  4. 校验逻辑复用播种校验的三级判定口径（阻断/提醒/通过）
- **验收标准**：
  1. 地块已有 6 月 1 日播种、10 月 1 日收获的玉米时，再排 9 月 15 日播种的小麦会被阻断
  2. 阻断提示写明冲突的是哪条记录、冲突区间、建议最早播期
  3. 同一用户两块地农忙期重叠时给出提醒，但不阻断
  4. 无关联地块时校验直接通过，不额外报错
- **对应目录**：`backend/service/plot/PlotHistory`（新建）/ `backend/api/SowCheckHandler` / `frontend/pages/index.html`

### 模块20：评分因子再增补与地理抽检
**任务编号：T20**
**优先级**：P2
- **任务描述**：
  1. 在现有七因子基础上按数据可得性增补：土壤质地（SoilGrids）、水源可达性（最近水体/渠道距离）、交通可达性（最近道路等级）
  2. 新增因子必须具备真实数据源，取不到时退出评分并重新归一，不允许用默认值顶替
  3. 建立地理抽检机制：抽取 20 个已知地块，人工核对坡度、坡向、面积是否合理，形成回归基线
  4. 因子说明页展示每个因子的数据来源、算法与权重
- **验收标准**：
  1. 数据齐全时因子数 ≥ 9，权重归一后合计 = 1.00
  2. 任一新增因子取不到时，其余因子权重重算，总分不出现 null 或 0
  3. 抽检的 20 个地块中，坡度与坡向人工核对一致率 ≥ 90%
  4. 因子说明页可看到每个因子的来源与算法说明
- **对应目录**：`backend/api/PlotAnalyzeHandler` / `backend/service/geo/` / `docs/`

### 模块21：传感器接口拉取与设备告警
**任务编号：T21**
**优先级**：P2
- **任务描述**：
  1. 后端新增传感器代理接口，替前端拉取用户填写的设备地址，规避跨域与密钥暴露
  2. 定时任务按设备配置的间隔拉取读数并入库，取代手动录入为主的使用方式
  3. 设备离线判定：超过 N 个周期无新数据标"离线"，并在设备列表提示
  4. 读数触发阈值时生成提醒，接入已落地的提醒中心（分类、分级、开关与已读直接复用）
- **验收标准**：
  1. 配置一个返回 JSON 的设备地址后，系统能按间隔自动取到读数
  2. 设备超过设定周期无数据时标"离线"，并说明最后在线时间
  3. 溶氧低于阈值时自动生成一条高风险提醒
  4. 拉取失败不影响手动录入，也不影响已有读数展示
- **对应目录**：`backend/api/SensorProxyHandler`（新建）/ `backend/service/sensor/`（新建）/ `frontend/assets/js/sensors-store.js`

### 模块22：养殖成本与产出核算
**任务编号：T22**
**优先级**：P3
- **任务描述**：
  1. 鱼塘按放养量、规格、成活率、饲料系数估算养殖成本与产出
  2. 支持记录实际投喂量、死淘数量、出塘规格与售价，算出本塘盈亏
  3. 与养殖日历联动：起捕节点提示"按当前规格与行情估算可出塘"
  4. 未填实际数据时只给区间估算，并标注"估算值，非实际账目"
- **验收标准**：
  1. 录入放养量、规格、饲料单价后能看到成本构成（苗种/饲料/电费/药费）
  2. 录入实际出塘数据后，盈亏与手算一致
  3. 估算值与实际值在界面上分开呈现，不混为一谈
  4. 起捕节点能给出是否适合出塘的判断依据
- **对应目录**：`backend/service/aqua/AquaCost`（新建）/ `frontend/assets/js/my-plots.js`

### 模块23：存储层可切换（文件 / MySQL）
**任务编号：T23**
**优先级**：P3
- **任务描述**：
  1. 在现有文件存储之外提供 MySQL 后端，通过配置切换，业务接口保持不变
  2. 两种后端行为一致：地块、作物、设备、提醒、账号数据的读写与删除
  3. 提供一次性迁移脚本与回滚说明，切换前可先在副本上演练
- **验收标准**：

  2. 切换配置后服务可正常启动，健康检查与「地块 → 日历 → 我的作物」主链路通过
  3. 迁移脚本可重复执行，不产生重复记录
  4. 切换失败可回滚到文件存储，数据不丢
- **对应目录**：`backend/store/`（新建）/ `deploy/`

## 五、开发与认领规则

1. **全栈认领**：每人认领完整功能模块，从数据、后端接口到前端页面全链路负责
2. **优先级顺序**：
   - 第一批（用户主链路）：T17 指导换算、T19 茬口校验
   - 第二批（判断质量）：T16 病害问诊、T20 因子增补
   - 第三批（档案与设备）：T21 传感器拉取、T22 养殖核算
   - 第四批（体验与工程）：T18 工程兜底、T23 持久化
3. **提交规范**：每个模块完成后提交对应目录代码，附带自测说明与验收条目逐条对照
4. **诚实性红线**（评审必查）：
   - 取不到的数据不得用默认值参与评分
   - 模型推算值必须标注"估算"并说明依据
   - 前端不得在接口失败时编造兜底分数或结论
5. **联调节点**：第一批完成后做一次「地块 → 日历 → 指导 → 我的作物」主链路联调；第三批完成后做档案与设备联调；第四批完成后做断网与跨设备联调（工单与提醒闭环已落地）
6. **验收节点**：每批完成后按验收标准逐条勾选，未达标不得标记完成

## 六、最终验收标准

1. 8 个任务（T16–T23）按各自验收标准可复现验证
2. 核心接口 p95 < 2s，外部依赖（DEM、天气、土壤、归档气象、设备接口）均具备三档降级
3. 用户主链路「我的地块 → 种植推荐 → 农事日历 → 我的作物 → 病害检查 → 客服」完整可走通，且数据在各环节之间连贯
4. 任一页面在断网、数据缺失、部分数据三种异常下都不白屏、不编造结论
5. 同一业务概念只有一处实现：区划、播季、面积换算、鱼种、上游解析、气候常年值
6. 提醒、工单、节点改期三条闭环均可跨会话使用，不依赖单次页面会话
7. 数据可跨设备访问，服务不可用时可降级读本地并明确提示
8. 公网地址可正常访问，账号与超管后台可用
