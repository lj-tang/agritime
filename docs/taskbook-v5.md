## 二、V5 目标

三条主线，按优先级排序：

1. **让提醒替用户盯着天气**（T19）：用户不需要每天打开日历，系统在"作物正处在敏感期 + 天气要出事"
   的时候才提醒，且每条提醒都说得清"为什么现在提醒你"。
2. **让数据可追溯**（T16）：每个展示数值都能回答来源、更新频率、取不到时怎么办。
3. **让状态可观测、数据可跨设备**（T17/T18）：p95、上游健康、缓存命中率可见；地块与作物不再锁在单机浏览器。

### 3.1 本轮已修复（提交 `f9be1c9`、`7fc5c2d`、`b70abab`）

| # | 缺陷 | 根因 | 影响 | 修法 |
| --- | --- | --- | --- | --- |
| 1 | 匿名工单身份可伪造 | `ip()` 取 `X-Forwarded-For` **第一段**，而 nginx 用 `proxy_add_x_forwarded_for`，客户端自带的头排在前面 | 改个请求头就能冒充别人，读到对方的工单内容 | 优先 `X-Real-IP`（nginx 覆盖写入），退到 XFF **最后一段**，并校验格式；前端带 `X-Visitor-Id`，同一 NAT 下不同用户不再串号 |
| 2 | 一年多熟第二季与第一季重叠 | `shift = span/2`（番茄 120 天周期平移 90 天） | 日历上"第一季采收"和"第二季播种"撞在同一天，自相矛盾 | 改为 `span + 7`（多茬 `span + 3`），第二季接在第一季收完之后 |

## 六、T19 气象智能提醒（核心）

### 6.1 为什么不做固定日期推送

V4 的提醒是"用户在某天手动给节点设一个闹钟"。问题在于：

- 与天气无关。降温了照样提示"今天施肥"，下雨了照样提示"今天打药"。
- 与生长阶段无关。苗期和花期用同一套阈值，花期霜冻这种要命的事反而没有提醒。
- 用户很快学会忽略。

T19 的判定是**两个条件同时成立才触发**：

```
当前物候阶段 ∈ 规则允许的阶段
        AND
未来 N 天气象指标满足阈值
        ↓
生成提醒（附带触发依据与实操建议）
```

任一条件不满足就不打扰。这也是"智能"和"定时"的区别。

### 6.2 数据流

```
地块（T17 后在服务端；之前由前端每日首次打开时上报）
   ↓ crop / sowDate / lat / lon / type
物候阶段判定（stage-map + 时间线节点 + 距播种天数兜底）
   ↓ stage ∈ {sowing, seedling, vegetative, flowering, fruiting, maturity, harvest}
未来 15 天日值天气（扩展后的 WeatherWindow.Daily）
   ↓ temp_max/min、rain_sum、rain_hours、humidity_mean、wind_max、soil_moisture
规则引擎逐条匹配（data/alerts/rules.json）
   ↓ 命中 → 计算 risk（高/中/低）
去重与升级（同 plot+rule+首日 72h 内不重复；升级立即重推）
   ↓
三类提醒 → 高风险推送 / 中低风险时间线标记 + 提醒中心
```

### 6.3 T19-0 数据补口（前置，必须最先做）

当前 `ComputeStub.fetchOsm` 只取 4 个日值：
`precipitation_sum, wind_speed_10m_max, temperature_2m_max, temperature_2m_min`。

**必须扩到 8 个**（已实测 Open-Meteo 支持）：

```
&daily=precipitation_sum,precipitation_hours,wind_speed_10m_max,
       temperature_2m_max,temperature_2m_min,
       relative_humidity_2m_mean,relative_humidity_2m_max,weather_code
```

`WeatherWindow.Daily` 相应扩展：

```java
public record Daily(double rainMm, double windMs, double minTempC, double maxTempC,
                    double humidityMean, double precipHours, int weatherCode) {}
```

> 注意单位：`wind_speed_10m_max` 返回 **km/h**，现有代码虽按 km/h 解析却把字段命名为 `windMs`，
> 属于历史命名问题，T19-0 一并改成 `windKmh`，避免规则里把 30km/h 当 30m/s 用。

### 6.4 规则模型

`data/alerts/rules.json`：

```json
{
  "version": "1.0.0",
  "rules": [
    {
      "id": "tomato_late_blight",
      "type": "disease",
      "name": "番茄晚疫病风险",
      "crops": ["番茄"],
      "stages": ["flowering", "fruiting"],
      "windowDays": 3,
      "conditions": [
        { "metric": "humidityMean", "op": ">=", "value": 85, "days": 2 },
        { "metric": "tempMean", "op": "between", "value": [15, 22], "days": 2 }
      ],
      "risk": {
        "high": "humidityMean >= 90 && rainSum >= 10",
        "medium": "default"
      },
      "advice": [
        "雨前抢喷保护性杀菌剂（代森锰锌 80% 可湿性粉剂 100g/亩）",
        "及时摘除病叶并带出田外销毁，不要随手丢在畦沟",
        "棚内加强通风，避免傍晚浇水，缩短夜间叶面结露时间"
      ],
      "basis": "病害库 tomato_late_blight 的发生条件：低温高湿",
      "source": "disease-library:tomato_late_blight"
    }
  ]
}
```

**指标字典**（引擎只认这些，新增指标需改代码）：

| metric | 含义 | 单位 | 来源 |
| --- | --- | --- | --- |
| `tempMax` / `tempMin` / `tempMean` | 日最高/最低/平均气温 | ℃ | daily |
| `rainSum` | 窗口累计降水 | mm | daily 累加 |
| `rainDays` | 窗口内有有效降水（≥0.1mm）的天数 | 天 | daily |
| `rainHours` | 窗口累计降水时长 | 小时 | daily 累加 |
| `humidityMean` | 窗口平均相对湿度 | % | daily 均值 |
| `windMax` | 窗口最大风速 | km/h | daily |
| `soilMoisture` | 0–1cm 土壤体积含水率 | m³/m³ | current |
| `dryDays` | 窗口内连续无有效降水天数 | 天 | 计算 |

**比较算子**：`>=` `<=` `>` `<` `between` `>=_consecutive`（连续 N 天满足）。
`risk` 是极小的表达式，引擎只支持 `&&` `||` 与上述 metric 比较，
**不做通用表达式求值**（不引脚本引擎，保持零依赖）。

### 6.5 物候阶段判定

优先级从高到低：

1. **规程节点**：`data/alerts/stage-map.json` 把 `opType + 标题关键词` 映射到阶段，例如
   `{"opType":"fertilize","keyword":"苗期"}` → `seedling`。
2. **进度兜底**：`已过天数 / totalDays` 落在
   `[0,0.15) 苗期 / [0.15,0.5) 营养生长 / [0.5,0.75) 开花结果 / [0.75,1) 成熟`。
3. **缺属性**：只用第 2 条默认分档，并在提醒里标 `stageSource: "progress"`。

> 现状 `crop-protocols.json` 的节点没有 `stage` 字段。T19 不强制改数据，
> 先用关键词映射 + 进度兜底，后续补 `stage` 字段即可平滑升级。

### 6.6 风险分级

| 级别 | 判定 | 典型场景 | 触达 |
| --- | --- | --- | --- |
| **高** | 规则 `risk.high` 成立，窗口 ≤3 天，可能明显减产 | 花期霜冻、暴雨内涝、连续高湿+适温（晚疫） | 页面横幅 + 浏览器通知 + 铃铛红点；同一条 24h 内只推一次 |
| **中** | 规则命中但未达 high | 干热风、持续高温、土壤过干、大风 | 时间线节点标记 + 提醒中心列表，不弹窗 |
| **低** | 窗口期类，或风险刚冒头 | "11/2–11/4 适合施药" | 只在提醒中心与时间线，静默 |

**免打扰**：22:00–07:00 不推高风险，07:00 后补推并合并成一条摘要。

### 6.7 去重、升级与过期

- `dedupeKey = plotId + ruleId + windowStart`
- 同一 key 72 小时内不重复创建；命中已有提醒时只更新 `lastSeenAt`
- 风险由 medium→high：更新原提醒，`escalated=true`，**立即重推**（不受 24h 限制）
- `expiresAt = windowEnd + 1 天`；过期移出列表（数据保留 7 天供回溯）
- 天气取不到时**不评估**，返回 `evaluated:false` 与原因，绝不"没数据 = 没风险"

### 6.9 前端交互（对齐主流网页）

| 行为 | 规范 |
| --- | --- |
| 通知权限 | **只在用户点击「开启天气推送」时** `Notification.requestPermission()`；不允许页面加载时自动弹（Chrome 会静默拒绝并记一次违规） |
| 铃铛 | 顶栏固定入口，未读显示数字红点，超过 9 显示 `9+`；点击进入提醒中心 |
| 提醒中心 | 按风险倒序，分「今天 / 本周 / 更早」三组；支持单条已读、全部已读、按类型筛选 |
| 时间线标记 | 中低风险在对应日期节点打角标（颜色随风险），点击展开触发依据 |
| 地块详情 | 该地块当前生效的提醒置顶，含"为什么"三行摘要 |
| 空状态 | 「未来 7 天暂无需关注的天气风险」+ 上次评估时间 |
| 失败降级 | 天气取不到时明确显示「今日未能获取天气，暂不评估」，提供重试；**不显示"无风险"** |
| 退订 | 三类独立开关 + 「暂停 7 天」；关闭后历史仍可查，只是不再新增/推送 |
| 首次引导 | 第一次进提醒中心用一条示意提醒说明三类含义，可关闭 |

### 6.10 规则样例（首批 12 条，覆盖三类）

| 类型 | 规则 | 作物 | 阶段 | 触发条件（窗口 3 天） |
| --- | --- | --- | --- | --- |
| 病害 | 番茄晚疫病 | 番茄 | 开花/结果 | 湿度均值 ≥85% 连续 2 天 且 均温 15–22℃ |
| 病害 | 番茄灰霉病 | 番茄 | 开花/结果 | 湿度均值 ≥90% 连续 2 天 且 均温 18–23℃ |
| 病害 | 小麦条锈病 | 小麦 | 拔节/抽穗 | 湿度均值 ≥80% 连续 3 天 且 均温 9–16℃ |
| 病害 | 水稻稻瘟病 | 水稻 | 分蘖/抽穗 | 降水时长 ≥20h 且 湿度 ≥85% |
| 病害 | 大蒜叶枯病 | 大蒜 | 返青后 | 湿度 ≥80% 连续 2 天 且 均温 12–20℃ |
| 病害 | 蚜虫迁飞 | 蔬菜/棉花 | 苗期/生长 | 连续 5 天无有效降水 且 均温 18–26℃ 且 风速 ≤10km/h |
| 灾害 | 花期霜冻 | 果树/油菜 | 开花 | 最低温 ≤2℃（高风险 ≤0℃） |
| 灾害 | 高温逼熟 | 水稻/玉米 | 灌浆 | 最高温 ≥35℃ 连续 3 天 |
| 灾害 | 暴雨内涝 | 通用 | 全期 | 单日降水 ≥50mm（中风险 25–50mm） |
| 灾害 | 大风倒伏 | 玉米/水稻 | 抽雄后 | 最大风速 ≥40km/h（约 6 级） |
| 农事 | 施药窗口 | 通用 | 全期 | 未来 3 天无降水 且 风速 ≤15km/h 且 最高温 ≤32℃ |
| 农事 | 灌溉窗口 | 通用 | 营养生长后 | 土壤含水率 ≤0.12 且 未来 2 天无有效降水 |

> 阈值取自公开农艺资料（病害发生的气象条件），属**经验阈值**；
> `rules.json` 每条带 `basis` 注明依据，界面不宣称"精准预测"。

### 6.11 验收标准

1. **阶段条件生效**：同一地块同一作物，苗期遇到与花期相同的阴雨天气，**不产生**晚疫病提醒。
2. **阈值可核对**：提醒 `trigger.metrics` 的数值与同时刻天气接口一致（误差 ≤0.1）。
3. **推送节流**：同一条高风险提醒 24h 内最多推送一次；风险升级立即重推并 `escalated=true`。
4. **分类开关**：关闭"病害风险"后病害类为零，灾害类不受影响。
5. **分级触达**：中低风险不出现在浏览器通知里，只在时间线与提醒中心。
6. **免打扰**：22:00–07:00 不推高风险，次日 07:00 合并补推。
7. **建议可执行**：每条 ≥2 条建议，含"做什么 + 怎么做 + 剂量/时机"。
8. **失败不装没事**：天气不可用时 `evaluated:false` 并说明原因，前端显示"暂不评估"。
9. **规则可测**：给定固定天气 fixture，引擎输出确定集合，单测覆盖 ≥10 条规则。

## 九、开发规则

1. 一个模块一次提交，commit 说明「做了什么 / 为什么 / 怎么验证」。
2. **数据红线**：新增展示数据必须同步登记 `data/sources/registry.json`。
3. 每个模块至少补 3 条断言；后端改动必须过 `deploy.sh` 编译（编译失败不会重启，线上不受影响）。
4. **不允许在服务器上改文件**：`deploy.sh` 会 `reset --hard`。
5. 规则类改动必须附 fixture 单测，禁止"调完看感觉"。

## 十一、风险与外部依赖

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 域名未备案 | HTTPS 不可用，浏览器通知在 http 下受限 | `enable-https.sh` 已就绪；通知在 http 下降级为站内横幅 |

| 浏览器通知权限被拒 | 高风险触达不到 | 站内横幅 + 铃铛红点兜底，不依赖通知权限 |
| 大模型生成规程慢 | 新作物首次请求 202 重试 | 已改后台任务 + 落盘缓存，前端自动重试 |
