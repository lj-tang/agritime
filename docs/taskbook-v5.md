> **V5 变更说明（相对 V4）**：
>
> V4 解决的是"功能有没有"，V5 解决的是"功能准不准、连不连得上"。四版下来仍有四类硬伤：
>
> 1. **判断不设防**：日历对输入照单全收，推荐不看地点，病害给个 0.42 的伪精确分数 —— 系统在替用户做它没能力做的判断。

> 4. **工程欠账**：23 处时间调用只有 2 处显式时区，天气失败仍返回一份看起来正常的日历，所有档案都存在浏览器里。
>
> 本版任务全部指向这四类问题，不含新建大模块。

## 一、项目整体目标

围绕**判断可信、数据连通、闭环可用**三条主线补齐：

- **判断可信**：每个结论都能追溯到数据来源与计算口径；说不准的地方明确说"说不准"，不用默认值蒙混。
- **数据连通**：同一份数据在推荐、日历、指导、地块之间流动，用户填一次就够；跨会话、跨设备不丢。
- **闭环可用**：提醒能落地、工单能流转、节点能调整、收获能核算 —— 用户在这个系统里能把一季农活走完。

性能与降级要求沿用 V4：核心接口 p95 < 2s，外部依赖具备三档降级。

## 三、功能任务拆解

### 模块16：评分因子再增补与地理抽检
**任务编号：T16**
**优先级**：P2
- **任务描述**：
  1. 在现有七因子基础上按数据可得性增补：土壤质地（SoilGrids）、水源可达性（最近水体/渠道距离）、交通可达性（最近道路等级）
  2. 新增因子必须具备真实数据源，取不到时退出评分并重新归一，不允许用默认值顶替
  3. 建立地理抽检机制：抽取 20 个已知地块，人工核对坡度、坡向、面积是否合理，形成回归基线
  4. 因子说明页展示每个因子的数据来源、算法与权重
- **验收标准**：
  1. 数据齐全时因子数 ≥ 9，权重归一后合计 = 1.00
  2. 任一新增因子取不到时，其余因子权重重算，总分不出现 null 或 0
  3. 抽检的 20 个地块中，坡度与坡向人工核对一致率 ≥ 90%
  4. 因子说明页可看到每个因子的来源与算法说明
- **对应目录**：`backend/api/PlotAnalyzeHandler` / `backend/service/geo/` / `docs/`

---

### 模块17：传感器接口拉取与设备告警
**任务编号：T17**
**优先级**：P2
- **任务描述**：
  1. 后端新增传感器代理接口，替前端拉取用户填写的设备地址，规避跨域与密钥暴露
  2. 定时任务按设备配置的间隔拉取读数并入库，取代手动录入为主的使用方式
  3. 设备离线判定：超过 N 个周期无新数据标"离线"，并在设备列表提示
  4. 读数触发阈值时生成提醒，接入已落地的提醒中心（分类、分级、开关与已读直接复用）
- **验收标准**：
  1. 配置一个返回 JSON 的设备地址后，系统能按间隔自动取到读数
  2. 设备超过设定周期无数据时标"离线"，并说明最后在线时间
  3. 溶氧低于阈值时自动生成一条高风险提醒
  4. 拉取失败不影响手动录入，也不影响已有读数展示
- **对应目录**：`backend/api/SensorProxyHandler`（新建）/ `backend/service/sensor/`（新建）/ `frontend/assets/js/sensors-store.js`

---

### 模块18：存储层可切换（文件 / MySQL）
**任务编号：T18**
**优先级**：P3
- **任务描述**：
  1. 在现有文件存储之外提供 MySQL 后端，通过配置切换，业务接口保持不变
  2. 两种后端行为一致：地块、作物、设备、提醒、账号数据的读写与删除
  3. 提供一次性迁移脚本与回滚说明，切换前可先在副本上演练
- **验收标准**：
  1. 同一份数据在 file / mysql 两种模式下读写结果一致
  2. 切换配置后服务可正常启动，健康检查与「地块 → 日历 → 我的作物」主链路通过
  3. 迁移脚本可重复执行，不产生重复记录
  4. 切换失败可回滚到文件存储，数据不丢
- **对应目录**：`backend/store/`（新建）/ `deploy/`

## 五、开发与认领规则

1. **全栈认领**：每人认领完整功能模块，从数据、后端接口到前端页面全链路负责
2. **优先级顺序**：
   - 第一批（判断质量）：T16 因子增补
   - 第二批（设备与档案）：T17 传感器拉取
   - 第三批（存储层）：T18 持久化
3. **提交规范**：每个模块完成后提交对应目录代码，附带自测说明与验收条目逐条对照
4. **诚实性红线**（评审必查）：
   - 取不到的数据不得用默认值参与评分
   - 模型推算值必须标注"估算"并说明依据
   - 前端不得在接口失败时编造兜底分数或结论
5. **联调节点**：第一批完成后做一次「病害 → 地块 → 推荐」判断链路联调；第二批完成后做设备与告警联调；第三批完成后做断网与跨设备联调（指导换算、茬口校验、养殖核算、工单与提醒闭环已落地）
6. **验收节点**：每批完成后按验收标准逐条勾选，未达标不得标记完成

## 六、最终验收标准

1. 3 个任务（T16–T18）按各自验收标准可复现验证
2. 核心接口 p95 < 2s，外部依赖（DEM、天气、土壤、归档气象、设备接口）均具备三档降级
3. 用户主链路「我的地块 → 种植推荐 → 农事日历 → 我的作物 → 病害检查 → 客服」完整可走通，且数据在各环节之间连贯
4. 任一页面在断网、数据缺失、部分数据三种异常下都不白屏、不编造结论
5. 同一业务概念只有一处实现：区划、播季、面积换算、鱼种、上游解析、气候常年值
6. 提醒、工单、节点改期三条闭环均可跨会话使用，不依赖单次页面会话
7. 数据可跨设备访问，服务不可用时可降级读本地并明确提示
8. 公网地址可正常访问，账号与超管后台可用
